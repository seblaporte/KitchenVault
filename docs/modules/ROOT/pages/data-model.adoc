== Tables de jointure

* `recipe_category` : liaison Recipe ↔ Category (many-to-many)
* `chapter_recipe` : liaison Chapter ↔ Recipe avec `sort_order` (many-to-many ordonné)
* `recipe_note` : collection de notes texte par recette
* `recipe_utensil` : collection d'ustensiles par recette

== Plan de repas et liste de courses

`MealPlanEntry` et les tables `shopping_list*` sont détaillées respectivement dans xref:menu-plan.adoc[Plan de repas] et xref:shopping-list.adoc[Liste de courses]. Comme pour `Recipe`, ces entités conservent un `recipe_id_snapshot`/`recipe_name_snapshot` pour rester exploitables même si la recette source est supprimée.

`WeeklyPlanSession` (colonne `pending_changes` en jsonb) suit l'état de conversation de l'assistant IA de planification hebdomadaire — voir xref:ai.adoc[Assistant IA culinaire].

Les tables liées à la recherche sémantique (`recipe_embedding_store`, pgvector) et à la mémoire de conversation du chat (`chat_message`) sont documentées dans xref:ai.adoc[Assistant IA culinaire] et ne sont pas reprises ici.

== Stratégie d'upsert

Les identifiants Cookidoo (`id`) sont utilisés comme clés primaires pour permettre un upsert natif via `save()` JPA :

* Si la recette est absente → INSERT
* Si la recette est présente et son `last_synced_at` est plus ancien que le seuil configuré (`cookidoo.sync.resync-after-hours`) → UPDATE complet
* Si la recette est fraîche → pas de requête vers Cookidoo
