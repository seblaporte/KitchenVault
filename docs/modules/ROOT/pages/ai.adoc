= Assistant IA culinaire
:description: Vue d'ensemble des fonctionnalités IA de KitchenVault (LangChain4J, OVH AI Endpoints, RAG)

== Vue d'ensemble

KitchenVault intègre trois fonctionnalités IA indépendantes, chacune pilotée par son propre *agent LangChain4J* :

[cols="2,3,1,1,3", options="header"]
|===
|Fonctionnalité |Rôle |RAG |Mémoire |Endpoint

|Planification hebdomadaire
|Génère et ajuste le menu de la semaine (déjeuners/dîners) à partir de contraintes en langage naturel — voir xref:ai-meal-planner.adoc[]
|Oui
|Oui (40 messages)
|`POST /api/v1/chat/meal-plan-week`

|Suggestion de recettes
|Chat libre pour trouver une recette par recherche sémantique — voir xref:ai-recipe-chat.adoc[]
|Oui
|Oui (20 messages)
|`POST /api/v1/chat/recipe`

|Liste de courses
|Fusionne, catégorise et dé-doublonne les ingrédients des recettes planifiées — voir xref:ai-shopping-list.adoc[]
|Non
|Non
|Interne (`ShoppingListService.consolidate()`)
|===

Chaque agent est une interface Java annotée, dont LangChain4J génère l'implémentation au démarrage via `AgenticServices.agentBuilder(...)`.
Il n'y a *pas* d'appel d'outils (`@Tool`) dans l'implémentation actuelle : chaque agent retourne directement un objet structuré (un `record` Java), que le service métier appelant utilise pour écrire en base — l'IA ne touche jamais la base de données elle-même.

Cette page décrit l'infrastructure partagée par les trois fonctionnalités : le modèle de langage, la recherche sémantique (RAG), la mémoire de conversation et la configuration. Le détail de chaque fonctionnalité est documenté sur sa page dédiée.

== Stack technique

* *LangChain4J `1.13.1`* (+ module `langchain4j-agentic` `1.13.1-beta23`) — définition des agents, sortie structurée, RAG, mémoire.
* *OVH AI Endpoints* — fournisseur unique pour le LLM et les embeddings, via une API compatible OpenAI. LangChain4J s'y connecte avec les classes standard `OpenAiChatModel` / `OpenAiEmbeddingModel` (aucune intégration spécifique OVH n'est nécessaire).
* *pgvector* — extension PostgreSQL pour le stockage et la recherche vectorielle (RAG).

== Recherche sémantique (RAG) et embeddings

La planification hebdomadaire et le chat de suggestion de recettes s'appuient tous les deux sur la recherche sémantique : à chaque appel, LangChain4J injecte automatiquement dans le contexte du LLM les recettes les plus proches sémantiquement du message de l'utilisateur, sans que l'agent ait besoin d'appeler un outil de recherche. L'indexation ci-dessous est commune aux deux ; le mécanisme de récupération diffère en revanche entre les deux agents (voir <<Recherche>>).

=== Indexation

`RecipeEmbeddingService.indexAllRecipes()` reconstruit l'intégralité de l'index à chaque appel — il n'y a pas de mise à jour incrémentale :

[plantuml]
....
@startuml
!theme plain
skinparam backgroundColor #FAFAFA
skinparam defaultFontSize 12
skinparam ArrowColor #555555

participant "SyncService /\nEmbeddingDelegate" as Trigger
participant "RecipeEmbeddingService" as Svc
participant "RecipeRepository" as Repo
participant "EmbeddingModel\n(bge-m3)" as Embed
database "pgvector\nrecipe_embedding_store" as PG

Trigger -> Svc : indexAllRecipes() [@Async]
Svc -> Repo : findAll()
Repo --> Svc : List<Recipe>
Svc -> Svc : toTextSegment(recipe) pour chaque recette

loop par lots de 25 segments
  Svc -> Embed : embedAll(chunk)
  Embed --> Svc : List<Embedding> (1024 dim.)
end

Svc -> PG : removeAll()
Svc -> PG : addAll(embeddings, segments)
@enduml
....

Déclenchement de l'indexation :

* automatiquement après chaque synchronisation Cookidoo réussie (`SyncService`, sync manuelle ou planifiée) ;
* manuellement via `POST /api/v1/embeddings/index` (202 Accepted, exécution asynchrone) — utile après un changement de modèle d'embedding ou une migration de schéma, indépendamment d'une sync Cookidoo.

Chaque recette est convertie en un `TextSegment` texte, par exemple :

----
ID: 3f2a1c9e-... Recette: Gratin dauphinois. Difficulté: easy. Temps total: 75 min.
Ingrédients: pomme de terre, crème, gruyère, ail, muscade. Ustensiles: Four, Plat à gratin.
Valeurs nutritionnelles: Pour 100 g (portion) – energy: 180.0 kcal, protein: 4.2 g, fat: 12.0 g.
----

L'identifiant de la recette (`ID:`) est inclus dans le texte lui-même (pas seulement en métadonnée) car c'est ce que les agents utilisent pour retrouver l'UUID exact d'une recette suggérée par le LLM.

=== Recherche

Les deux agents RAG n'utilisent *pas* le même mécanisme de récupération :

* `RecipeSuggestionAgent` utilise le bean partagé `EmbeddingStoreContentRetriever` (`maxResults=10`, `minScore=0.6`) directement via `.contentRetriever(...)` — recherche vectorielle simple, sans filtrage.
* `WeeklyMealPlanAgent` utilise un `RetrievalAugmentor` dédié construit autour de `RoleAwareRecipeContentRetriever`, qui croise la recherche vectorielle avec les xref:ai-meal-planner.adoc#listes-de-recettes-et-retrieval-role-aware[listes de recettes de l'utilisateur] (favoris / à découvrir / à exclure) — voir le détail sur la page du planificateur.

Dans les deux cas, le LLM reçoit les recettes pertinentes injectées automatiquement dans son contexte, sans avoir à les demander explicitement via un outil.

=== Schéma de la table d'embeddings

[source,sql]
----
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE recipe_embedding_store (
    embedding_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    embedding    vector(1024) NOT NULL,
    text         text,
    metadata     jsonb
);
CREATE INDEX ON recipe_embedding_store USING hnsw (embedding vector_cosine_ops);
----

NOTE: Le schéma a évolué plusieurs fois (changesets Liquibase `006` à `010`) : forme initiale `id`/`recipe_id` propre à KitchenVault, puis alignement sur la forme attendue par défaut par `PgVectorEmbeddingStore` (`embedding_id`/`embedding`/`text`/`metadata`), puis changements de dimension 384 → 768 → 1024 au fil des changements de modèle d'embedding. La dimension actuelle (1024) correspond à `bge-m3`.

== Mémoire de conversation

La mémoire est persistée en PostgreSQL (table `chat_message`) via `PostgresChatMemoryStore`, une implémentation maison de l'interface `ChatMemoryStore` de LangChain4J (le stockage par défaut de LangChain4J est en mémoire process, donc perdu au redémarrage — d'où cette implémentation).

[plantuml]
....
@startuml
!theme plain
skinparam backgroundColor #FAFAFA
skinparam defaultFontSize 12
skinparam ArrowColor #555555

participant "Agent\n(WeeklyMealPlanAgent /\nRecipeSuggestionAgent)" as AI
participant "MessageWindowChatMemory" as Window
participant "PostgresChatMemoryStore" as Store
database "chat_message" as DB

AI -> Window : getMessages(sessionId)
Window -> Store : getMessages(sessionId)
Store -> DB : SELECT role, content\nWHERE session_id = ?\nORDER BY created_at ASC
DB --> Store : rows
Store --> Window : List<ChatMessage>\n(désérialisées depuis JSON)

note right of Window
  Fenêtre glissante :
  40 messages pour le planificateur,
  20 pour le chat de suggestion.
end note

AI -> Window : updateMessages(sessionId, messages)
Window -> Store : updateMessages(sessionId, messages)
Store -> DB : DELETE WHERE session_id = ?
Store -> DB : INSERT (role, content) × N
@enduml
....

Chaque message est sérialisé en JSON avec son rôle (`USER`, `AI`, `TOOL_EXECUTION_RESULT`, `SYSTEM`). Le rôle `TOOL_EXECUTION_RESULT` existe dans le store pour compatibilité avec l'API `ChatMemoryStore` de LangChain4J, mais n'est jamais produit actuellement puisqu'aucun agent n'utilise d'outils (`@Tool`).

[source,sql]
----
CREATE TABLE chat_message (
    id         bigserial PRIMARY KEY,
    session_id varchar(255) NOT NULL,
    role       varchar(50)  NOT NULL,   -- USER | AI | TOOL_EXECUTION_RESULT | SYSTEM
    content    text         NOT NULL,   -- JSON sérialisé
    created_at timestamptz  NOT NULL DEFAULT NOW()
);
CREATE INDEX ON chat_message (session_id, created_at);
----

== Configuration

Toutes les propriétés IA sont regroupées sous le préfixe `ai:` dans `application.yml` et exposées via l'enregistrement `AiProperties` (`@ConfigurationProperties(prefix = "ai")`).

[source,yaml]
----
ai:
  session:
    retention-days: 30                  # rétention des sessions/messages avant purge
    cleanup-cron: "0 0 2 * * *"         # planification de la purge

  ovh:
    api-key: ${OVH_AI_ENDPOINTS_ACCESS_TOKEN:}
    model-name: gpt-oss-120b
    base-url: https://oai.endpoints.kepler.ai.cloud.ovh.net/v1

  ovh-embedding:
    api-key: ${OVH_AI_ENDPOINTS_ACCESS_TOKEN:}
    model-name: bge-m3
    base-url: https://oai.endpoints.kepler.ai.cloud.ovh.net/v1
    dimension: 1024

  shopping-list:
    basic-necessities:                  # exclus de la liste de courses par défaut
      - eau
      - sel
      - poivre
      - huile
      - "huile d'olive"
      - sucre
      - farine
      - beurre
      - vinaigre
      - moutarde
      - levure chimique
      - bicarbonate
      - laurier
      - thym
      - paprika
      - cumin
----

Le LLM de chat et le modèle d'embedding partagent la *même* variable d'environnement `OVH_AI_ENDPOINTS_ACCESS_TOKEN` et la même URL de base OVH AI Endpoints — seuls les `model-name` diffèrent.

Le planificateur hebdomadaire utilise un `ChatModel` distinct (`temperature=0.3`, pour un menu plus varié) de celui du chat de suggestion et de la consolidation de liste de courses (`temperature=0.0`, pour des réponses déterministes), bien que les deux pointent vers le même modèle `gpt-oss-120b`.

== Nettoyage des sessions

`ChatSessionCleanupService` purge périodiquement les sessions et messages inactifs, pour éviter une croissance illimitée de `chat_message` et `weekly_plan_session` :

[source]
----
@Scheduled(cron = "${ai.session.cleanup-cron:0 0 2 * * *}")
purgeExpiredSessions()
  └── cutoff = now() - ai.session.retention-days (30 jours par défaut)
  └── DELETE chat_message   WHERE session_id IN (SELECT session_id FROM weekly_plan_session WHERE last_active_at < cutoff)
  └── DELETE weekly_plan_session WHERE last_active_at < cutoff
  └── DELETE chat_message   WHERE created_at < cutoff   -- messages orphelins (chat de suggestion, sans session planificateur)
----
